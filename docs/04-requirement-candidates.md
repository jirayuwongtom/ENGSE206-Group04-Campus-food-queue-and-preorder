# 04 — Requirement Candidates: Campus Food Queue and Preorder (Case 04)

> **Week 04** · Candidate ด้านล่างตั้งจาก Evidence Log และยังไม่ใช่ข้อกำหนดที่ผู้ใช้หรือเจ้าของร้านอนุมัติ คำตอบจาก stakeholder ใน E-01 ถึง E-08 เป็นการจำลอง จึงต้องตรวจสอบกับคนจริงก่อนนำไปยืนยันเป็น requirement

## 1. วิธีแปลง evidence เป็น candidate

1. อ้างอิงข้อมูลจาก E-ID ใน [Evidence Log](04-evidence-log.md)
2. แยกสิ่งที่ stakeholder ต้องการออกจากความสามารถที่ระบบอาจทำให้ได้
3. เก็บความเห็นที่ขัดกันไว้ให้เห็น และใช้สถานะ `Candidate` หรือ `Provisional` ตามหลักฐาน
4. ระบุเรื่องที่ต้องถามเพิ่ม พร้อมผู้ใช้หรือผู้มีอำนาจที่ควรยืนยัน

## 3. ทำไมรายการเหล่านี้ยังเป็น candidate

| RC | เหตุผลที่ยังไม่ final |
|---|---|
| RC-01 | E-07 มาจากลูกค้าจำลอง ยังไม่ได้ยืนยันกับนักศึกษาจริงว่าหมายเลขคิวและสถานะเป็นข้อมูลที่เพียงพอหรือไม่ |
| RC-02 | ความต้องการจำนวนคิวและเวลารอมาจากการจำลอง ยังไม่มีข้อมูลเวลาทำอาหารหรือวิธีคำนวณที่ตรวจสอบแล้ว โดยเฉพาะค่าคลาดเคลื่อน 5 นาที |
| RC-03 | E-05 กับ E-08 ขัดกันเรื่องสิทธิ์ยกเลิก ผล Option C ใน C-01 เป็นข้อเสนอชั่วคราว และเจ้าของร้านจริงยังไม่ได้ยืนยันนโยบาย |
| RC-04 | E-01, E-03 และ E-04 เป็นข้อมูลจำลอง ยังต้องตรวจขั้นตอนจริงของพนักงาน และไม่ควรสรุปกฎแทรกคิวจากหลักฐานนี้เพียงอย่างเดียว |
| RC-05 | E-02 เป็นข้อมูลจำลอง ยังไม่มีขั้นตอนจริงเมื่อวัตถุดิบหมด รวมถึงผลต่อออเดอร์ที่รับไปแล้ว |

## 4. ส่งต่อ Week 05 Backlog

| Week 04 RC | ย้ายไป Week 05? | สิ่งที่พบใน Backlog / งานที่ต้องตามต่อ |

| RC-01 | Yes / FR-01 | ย้ายเป็นการแสดงหมายเลขคิวและสถานะอาหาร; ยังควรตรวจหน้าจอกับลูกค้าจริง |
| RC-02 | Yes / FR-02 | อยู่ใน Backlog สถานะ Needs Follow-up; ต้องยืนยันวิธีประเมินเวลารอและเกณฑ์ความคลาดเคลื่อน |

## 5. ข้อควรจำ

- E-01 ถึง E-08 เป็นผลจากการจำลอง stakeholder ไม่ใช่คำยืนยันจากพนักงาน เจ้าของร้าน หรือลูกค้าจริง
- C-01 ยังเปิดอยู่; Option C เป็นเพียงทางเลือกชั่วคราวในบันทึกการเจรจา
- อย่าเพิ่มตัวเลข นโยบายคืนเงิน หรือกฎแทรกคิวจนกว่าจะมีแหล่งข้อมูลที่ยืนยันได้
- การย้าย candidate เข้า Week 05 ไม่ได้แปลว่า requirement นั้นได้รับอนุมัติแล้ว
