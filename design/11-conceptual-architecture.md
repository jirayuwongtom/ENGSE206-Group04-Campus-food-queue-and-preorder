## 5. NFR กระทบ container ไหน
ภาพตัวอย่างการเขียนสถานะจะเน้นความกระชับ โดยอ้างอิงถึง Open Issue (ของกลุ่มคุณใช้รหัส ISS) หรือส่งต่องานให้สัปดาห์ถัดไป สามารถปรับตารางใหม่ให้สั้นและตรงตามรูปแบบได้ดังนี้:

| NFR | ต้องการอะไร | ผลต่อ container | สถานะ |
| --- | --- | --- | --- |
| NFR-01 | ระบบแสดงผลการอัปเดตสถานะไปที่หน้าจอลูกค้าภายใน 3 วินาที| API Application ต้องรองรับการส่งข้อมูลให้ฝั่ง Client แบบ Real-time และ Mobile Application ต้องรับข้อมูลเพื่ออัปเดตหน้าจอได้ทันที | TBD — ISS-02 |
| NFR-02 | จัดเก็บเฉพาะข้อมูลจำเป็น โดยไม่เก็บข้อมูลประวัติการแพ้อาหาร| Database ต้องไม่มีโครงสร้างจัดเก็บข้อมูลสุขภาพ และ API Application ต้องไม่รับหรือบันทึกข้อมูลส่วนนี้ | TBD — ISS-03 |
| NFR-03 | หน้าจอฝั่งร้านค้ากดเปลี่ยนสถานะออเดอร์ได้สำเร็จในไม่เกิน 2 คลิก| Mobile Application — ออกแบบหน้าจอใน W12 | ส่งต่อ W12 |

## 6. Decision cards

**DEC-01 กติกาการยกเลิกออเดอร์และการตรวจสิทธิ์ต้องทำที่ API**

| หัวข้อ | รายละเอียด |
| --- | --- |
| **ตัดสินใจ** | ให้ API Application เป็นจุดเดียวที่ใช้เช็คว่าลูกค้ายกเลิกออเดอร์ได้ไหม (BR-01) ถ้าลูกค้ากดยกเลิกพร้อมกับที่ร้านกดรับออเดอร์พอดี ให้ยึดเวลาฝั่ง Server เป็นหลัก|
| **เพราะ (NFR / driver)** | ป้องกันร้านเสียต้นทุนทำอาหารฟรี และแก้ปัญหาข้อมูลสองฝั่งไม่ตรงกันตอนกดปุ่มพร้อมกัน (Race Condition)|
| **ทางเลือกที่ไม่เลือก** | ให้แอปมือถือเช็คสิทธิ์ฝั่งเดียว วิธีนี้เสี่ยงมากเพราะข้อมูลบนหน้าจอลูกค้ากับร้านอาจไม่อัปเดตตรงกันในเสี้ยววินาทีนั้น |
| **ผลที่ตามมา** | แอปมือถือทำหน้าที่แค่ซ่อนปุ่มยกเลิกเพื่อให้ใช้งานง่าย แต่การฟันธงว่ายกเลิกสำเร็จหรือไม่ต้องรอ API ตอบกลับมาเท่านั้น |

**DEC-02 ฐานข้อมูลเดียวคือแหล่งอ้างอิงลำดับคิวและสถานะ**

| หัวข้อ | รายละเอียด |
| --- | --- |
| **ตัดสินใจ** | เก็บข้อมูลออเดอร์และคิว (DR-01, DR-02) ไว้ใน Database ก้อนเดียวกัน และใช้ระบบ Transaction จัดการตอนเปลี่ยนสถานะ|
| **เพราะ (NFR / driver)** | จะได้เรียงคิวแบบ FIFO ได้แม่นยำ (FR-04, D2) และเช็คเงื่อนไขตอนยกเลิกออเดอร์ (BR-01) ได้ชัวร์โดยไม่ต้องกลัวข้อมูลขัดแย้งกัน|
| **ทางเลือกที่ไม่เลือก** | แยกคิวไปเก็บในหน่วยความจำชั่วคราวเพื่อให้ทำงานเร็วขึ้น วิธีนี้เสี่ยงคิวหายถ้าระบบล่ม และเขียนโค้ดยากขึ้นตอนเอาข้อมูลมาเช็คคู่กัน |
| **ผลที่ตามมา** | ต้องใช้ฐานข้อมูลที่รองรับ Transaction (เช่น PostgreSQL) และเวลาจะดึงคิวต้องดึงจากฐานข้อมูลนี้ที่เดียว|

**DEC-03 ทำแอปมือถือตัวเดียว แต่แสดงหน้าจอตามสิทธิ์ผู้ใช้**

| หัวข้อ | รายละเอียด |
| --- | --- |
| **ตัดสินใจ** | ให้ลูกค้าและพนักงานร้านใช้ Mobile Application ตัวเดียวกัน แต่ใช้การเช็คสิทธิ์ (Role) ล็อกอิน เพื่อแยกหน้าจอและเมนูให้ตรงกับประเภทผู้ใช้งาน|
| **เพราะ (NFR / driver)** | ทุกคนใช้มือถือเป็นหลักอยู่แล้ว (ACT-01 ถึง ACT-04) การทำแอปเดียวช่วยประหยัดเวลาเขียนโค้ด และตอบโจทย์พนักงานร้านที่ต้องการความรวดเร็ว (NFR-03) โดยไม่ต้องโหลดแอปหลายตัว|
| **ทางเลือกที่ไม่เลือก** | ทำแอปแยกของลูกค้าตัวนึง ของร้านตัวนึง วิธีนี้ทีมต้องดูแลโค้ดสองชุด และเสียเวลาตอนนำแอปขึ้น Store ถึงสองรอบ |
| **ผลที่ตามมา** | งานออกแบบหน้าจอ (W12) จะทำอยู่ในโปรเจกต์เดียวกัน การซ่อนเมนูจะทำบนแอปมือถือ แต่การตรวจสิทธิ์ตอนกดทำงานจริงยังไงก็ต้องไปเช็คที่ API เสมอ|
